## 읽는 법

각 리스크에는 **트리거**(이런 신호가 보이면)와 **대응**(그때 이렇게 한다)이 붙어 있습니다.
트리거를 미리 정해두면 “좀 더 지켜보자” 로 시간을 흘려보내지 않게 됩니다.

## 상위 리스크

### R1 · 기획서·컨셉 미반영 상태로 개발이 진행됨 — 심각도 높음 / 확률 높음

**지금 실제로 벌어지고 있는 리스크입니다.**
기획서 v6 와 컨셉 영상이 이 레포에 없어, 서비스 정의·기능 목록·디자인이 추정 상태입니다.

- **트리거** — D-12(9/04) 종료 시점에 <a href="{{ '/plan/overview/' | relative_url }}">01 개요</a>의 「사용자와 가치」 표가 여전히 비어 있음
- **영향** — 도메인 테이블 이름·AI 시나리오·디자인 토큰이 전부 미확정 → D-10 이후 재작업
- **대응** — ① 기반 영역(인증·인프라·구조·디자인 시스템 골격)을 먼저 소진해 대기 시간을 0으로 만든다 ② PM 이 D-13 안에 기획서를 레포에 넣는다 ③ D-12 까지 안 되면 PM 이 **구두로라도 5개 항목**(사용자·문제·해법·핵심기능 3개·화면 5개)을 확정 선언한다
- **담당** — 류준

### R2 · 14일 안에 MUST 를 못 끝냄 — 심각도 높음 / 확률 중간

- **트리거** — D-7(9/09) 알파에서 핵심 시나리오 완주 실패, 또는 MUST 완료율 60% 미만
- **대응** — <a href="{{ '/plan/scope/' | relative_url }}">02 범위</a>의 컷 순서대로 기계적으로 잘라낸다. 그 자리에서 논쟁하지 않는다
- **담당** — 류준

### R3 · 백엔드 1인 병목 — 심각도 높음 / 확률 높음

인증·프로필·도메인 2종·파일·권한이 전부 장민석에게 몰려 있습니다. **백엔드가 늦으면 3인이 동시에 멈춥니다.**

- **트리거** — D-11(9/05) 종료 시 인증 API 미완, 또는 웹·앱이 목데이터로 대기 중
- **대응** — ① API 계약(9/04)을 먼저 내서 클라이언트가 계약 기준으로 선행 개발 ② 신채연이 도메인 BC 하나를 넘겨받는다 (AI BC 는 D-8 이후 여유가 생김) ③ 그래도 안 되면 도메인 리소스 #2(M4)를 SHOULD 로 강등
- **담당** — 류준 · 장민석

### R4 · AI 응답 품질이 시연 수준에 못 미침 — 심각도 높음 / 확률 중간

- **트리거** — D-6(9/10) 평가셋 통과율 18/20 미만
- **대응** — ① 시나리오 범위를 좁힌다 (자유 대화 → 정해진 3가지 작업) ② RAG(S1) 를 잘라내고 프롬프트에 지식을 직접 넣는다 ③ 그래도 안 되면 AI 를 **보조 기능**으로 배치하고 일반 UI 로 같은 작업이 가능하게 한다
- **담당** — 신채연

### R5 · 앱 스토어 심사 지연 — 심각도 높음 / 확률 중간

우리가 통제할 수 없는 유일한 변수입니다. 심사에 며칠이 걸릴지 모릅니다.

- **트리거** — D-3(9/13) 제출 실패, 또는 D-1(9/15)까지 심사 미통과
- **대응** — ① **웹 먼저 오픈**한다. 9/16 서비스 오픈은 웹 기준으로 성립시킨다 ② 앱은 내부 테스트 트랙 링크로 대체 안내 ③ 심사 반려 사유(약관·개인정보·로그인 계정 미제공 등)를 D-4 에 선점검
- **담당** — 류준 · 이은상

### R6 · 통합 시점에 계약 불일치가 쏟아짐 — 심각도 중간 / 확률 높음

- **트리거** — D-9(9/07) 1차 통합에서 계약 이슈 5건 이상
- **대응** — 그날 백엔드는 **다른 일을 멈추고 계약 이슈만** 처리한다 (BE-15가 그래서 있는 항목). 통합은 미룰수록 비싸진다
- **담당** — 장민석

### R7 · AI 비용 폭증 — 심각도 중간 / 확률 중간

- **트리거** — 일일 사용량이 상한의 80% 도달
- **대응** — 캐싱(S5) 활성화 → 컨텍스트 길이 축소 → 모델 등급 하향 → 사용자당 일일 한도
- **담당** — 신채연 · 류준

### R8 · 인원 이탈 (질병·개인사정) — 심각도 높음 / 확률 낮음

14일 일정에서 1인 이탈은 전체의 20% 손실입니다.

- **트리거** — 하루 이상 작업 불가 통보
- **대응** — 백업 담당이 미리 정해져 있어야 한다 → 아래 표
- **담당** — 류준

| 이탈 시 | 1차 백업 | 근거 |
|---|---|---|
| 장민석 (백엔드) | 신채연 | 같은 백엔드 스택·구조 규약 공유 |
| 신채연 (AI) | 장민석 | 동일 |
| 김충식 (웹) | 이은상 | 같은 API 계약·디자인 토큰 |
| 이은상 (앱) | 김충식 | 앱을 컷하고 웹 오픈으로 전환 (R5 대응과 동일) |
| 류준 (PM) | 장민석 | 인프라 접근 권한을 **2인이 보유** (D-12까지) |

### R9 · 주말 번아웃 — 심각도 중간 / 확률 높음

9/05~9/06, 9/12~9/13 두 번의 주말이 모두 작업일입니다.

- **트리거** — 데일리 리뷰에서 이틀 연속 계획 대비 절반 미만 소화
- **대응** — 개인의 의지 문제로 다루지 않는다. **범위를 줄인다.** 야근으로 메우면 어디가 늦는지 안 보이게 된다
- **담당** — 류준
